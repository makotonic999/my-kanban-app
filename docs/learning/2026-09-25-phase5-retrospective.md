## 1. 技術的な学び

### CORS とプリフライトは「認証の外」に置く
ブラウザはプリフライト（`OPTIONS`）に `Authorization` ヘッダを **付けずに** 送る。
そのため CORS を認証の内側に置くと、プリフライトが認証で弾かれ本リクエストに到達できない。

```
正しい積み順（外 → 内）:
  CORS → Metrics → Mux → RequireAuth → Handler
  └ OPTIONS はここで 204 を返して打ち切る（認証に到達させない）
```

実挙動でも確認済み: 許可オリジン → `204` + 各ヘッダ、不許可オリジン → `Access-Control-Allow-Origin` 付与なし。

### 開発は Vite プロキシ、本番は CORS の二本立て
- **開発**: Vite の `/api` プロキシでブラウザから見て同一オリジン化 → CORS は実質不要。
- **本番**: CloudFront(フロント) と API のオリジンが異なる → サーバ側 CORS が必須。

両方を用意することで、開発の快適さ（同一オリジン）と本番の正しさ（明示的な allow-list）を両立。

### Vite の環境変数はビルド時に焼き込まれる
`VITE_API_BASE_URL` はランタイムではなく **ビルド時** に埋め込まれる。
→ CD では「ビルドステップ」で注入する必要がある（実行時 env では効かない）。詰まりやすい定番ポイント。

### 401 を型に落として一元処理
`api.ts` で 401 を `ApiError` として表現し、UI 側は「401 なら自動ログアウト」に一元接続。
認証失効の扱いがコンポーネントに散らばらない。

### デプロイ宛先は「output を真実源」に
`scripts/deploy-frontend.ps1` はバケット名 / Distribution ID を `terraform output` から動的取得。
ハードコードしないことで、ランダムサフィックス付きバケットや再作成にも追従できる。
